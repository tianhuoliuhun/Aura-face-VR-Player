## 1. 功能总览

| 功能 | 开关 | 可调项 | 生效范围 |
|---|---|---|---|
| **MEMC 插帧** | 设置 → 画质增强 → MEMC 插帧 | 目标帧率 **48 / 60 / 72 / 90 / 120** | **仅视频播放时** |
| **FSR 超分** | 设置 → 画质增强 → FSR 超分 | 规则模式（默认 / 自定义）+ 目标分辨率 6 档 | **仅视频播放时** |

> ⚠️ **两个开关在图片 / 全景浏览模式下都不生效** —— 启用判定基于**视频源分辨率**，
> 图片模式没有该信息。此时 FSR 开关虽然可以打开，但不会有任何效果，
> 副标题会显示「等待视频信息」。

两者都受「记忆模式」门控，设置会持久化。

## 2. FSR 超分

### 2.1 默认规则

判定基线 = **视频源分辨率的短边**（`min(width, height)`，横竖屏统一识别）：

| 源短边 | 结果 |
|---|---|
| **> 1440** | **不启用超分** |
| **= 1080** | 超分至 **1440p**（高度 1440） |
| **其余**（含 1440 本身） | 超分至 **1080p**（高度 1080） |

**边界保护**：在默认规则之上再加一层判断 —— **目标高度 ≤ 源短边时不启用**。
否则按字面规则，1440p 源会被「超分」到 1080p，那是**降画质**而非超分。

### 2.2 自定义规则

可选 6 档：`720p / 1080p / 1440p / 2160p / 3840p / 4320p`。

**优先级**：自定义规则**完全接管** —— 用户选了哪个档位就按哪个执行，
默认规则（含边界保护）**不再参与判定**，两者互斥、不叠加。

> ⚠️ 注意 `3840p` 并非标准 16:9 规格（16:9 下垂直 3840 对应宽度约 6827）。
> 本项目将其**显式定义**为 `7680×3840`。UI 上不显示这套参考宽高，
> 而是显示**实际生效尺寸**，避免口径歧义。

### 2.3 判定基线与边界保护

**档位的语义是「目标高度」，宽度一律按源宽高比推导**：

```
目标宽度 = round(目标高度 × 源宽 / 源高)
```

这样做的原因（v2.0.207 修复）：档位若按 16:9 写死宽高，非 16:9 片源会变形 ——
FSR 只改变分辨率、**不能改变画面比例**，输出纹理再被主 shader 按 UV 采样时，
比例不一致就直接拉伸。

| 源 | 档位 | 结果 |
|---|---|---|
| 1920×1080（16:9） | 2160p | 3840×2160 |
| 1920×960（2:1） | 4320p | **8640×4320**（保持 2:1） |
| 320×176（1.818:1） | 默认规则 → 1080p | **1964×1080** |

**纹理上限保护**：目标尺寸超出 `GL_MAX_TEXTURE_SIZE` 时**自动降级为不超分**。
否则 `glTexImage2D` 会静默失败，之后绑定到 0 号纹理 → **黑屏且无任何报错**。

## 3. MEMC 插帧

**目标帧率选项**：`48 / 60 / 72 / 90 / 120`（覆盖用户要求的 48~120 区间）。

> ⚠️ **目标帧率是「输出上限」而非保证值。** 它只能向下限制输出节奏，
> 无法把渲染循环帧率提上去。实际可达帧率受**屏幕刷新率**与**GPU 负载**限制。
> 例如模拟器屏幕只有 60Hz 时，选 120 不会有任何效果（此时节流不会生效，
> 等同于「不限制」，行为是正确的）。

**实现链路**：

```
OES 纹理 ──拷贝──▶ 2D 双帧持有(prev / curr)
                      │
                      ├─▶ ME 运动估计（块匹配）→ MV 场
                      │
                      ├─▶ 场景切换检测（1x1 帧差回读）
                      │
                      └─▶ MC 运动补偿插帧 → 输出
```

- **运动估计**：3 步菱形搜索（十字 r → 对角 r/2 → 中等 r/4）+ 2 轮 ±1 精修。
  单步全搜索在 r=16 时需要 1089 次 SAD，3 步法只要 21 次却能达到接近的精度。
  块大小 16×16，块内取 4×4=16 个采样点；**MV 场按块网格降采样**（每块一个 MV），
  MC 采样时用 `GL_LINEAR` 自动插值回全分辨率。
- **运动补偿**：双向补偿 —— 前向在 prev 上按 `phase` 反向偏移、反向在 curr 上按
  `1-phase` 正向偏移；两方向差异大 = 出现遮挡，此时**退化为线性混合**
  （宁可糊一点也不要撕裂，这是刻意的保护逻辑）。
- **场景切换**：帧差超过阈值时强制 `phase = 1` 跳过插帧，
  否则会插出「两个场景叠加」的严重鬼影。检测结果通过 **1×1 的帧差回读**获得
  —— 这是整条增强链里**唯一**的 `glReadPixels`，代价可忽略。
- **相位计算**：`phase = (now − 一个源帧间隔 − prevTime) / (currTime − prevTime)`。

  > ⚠️ **不要改回 `(now - prevTime) / (currTime - prevTime)`。**
  > 新帧到达时 `currTime` 就是本帧刚取的 `now`，那个公式恒等于 1；
  > 只要渲染循环帧率 ≥ 源帧率，每帧都会命中该分支，**插帧永远不会发生**
  > （v2.0.206 的实测现象：logcat 连续打印 `phase=1.00`）。
  >
  > 减去一个源帧间隔后相位才会真正在 [0,1] 之间推进。代价是**输出延迟一个源帧间隔**
  > —— 这是 MEMC 的固有代价（30fps 源约 33ms，肉眼不可察）。

## 4. 管线顺序：为什么 MEMC 必须在前

```
源帧 ──▶ MEMC（改帧数与时间戳）──▶ FSR（只改空间尺寸）──▶ 主渲染
```

三条理由：

1. **成本** —— 运动估计的成本 ∝ 像素数 × 搜索半径²。
   先超分到 4K 再做 ME，成本是「先 MEMC 后超分」的 **16 倍**，实时跑不动。
2. **质量** —— 超分会**生成**原本不存在的细节；若先超分再块匹配，
   MV 会去匹配这些假细节，矢量变得不可信。反过来，MEMC 输出（时域对齐后的帧）
   比原帧更干净，超分在这个输入上效果更好。
3. **时序语义** —— MEMC 属于时间域（改时间戳），超分属于空间域（不碰时间戳）。
   时间域放上游，时间戳就只需在一处管理。

## 5. 实现要点

### 5.1 主 shader 零改动接入

主 shader 里 `uIsVideo` 只有「采样哪张纹理」这一处用途：

```glsl
if (uIsVideo == 1) color = texture2D(uSamplerVideo, tc); else ...
```

而 `imageProgram`（未定义 `VIDEO_OES` 的那份变体）中 `uSamplerVideo` 被声明为普通
`sampler2D`。于是只要：

1. program 选 `imageProgram`
2. 把增强纹理绑到 `samplerVideo` 的槽位（`TEXTURE1`）
3. `uIsVideo` 置 1

主 shader 就直接采样增强结果 —— **不必给主 shader 加任何分支或宏**。
这避免了改动主 shader 里 15 处采样点带来的回归风险。

> ⚠️ 不要用 `videoProgram`（OES 变体）接增强纹理：那个槽位声明为
> `samplerExternalOES`，绑 2D 纹理属未定义行为。

### 5.2 增强链的 GL 状态契约

`runVideoEnhance()` 结束时会把 framebuffer 绑回 0 并恢复 viewport ——
调用方可以当作「什么都没发生过」，随后自行绑定主渲染目标。

### 5.3 目标帧率节流

未到下一帧的时间点时**复用上一帧的增强纹理**，但**不跳过 `onDrawFrame` 的绘制**。
画面仍按屏幕刷新率重绘（投影矩阵、陀螺仪姿态照常更新），
所以 VR 下转头依旧跟手，只是视频内容停留在上一张。

> 若直接 `return` 掉整个 `onDrawFrame`，转头的卡顿会非常明显。

## 6. 性能与已知限制

- **两者都是 GL 重负载**：
  - MEMC ≈ 每块 22 次 SAD × 16 采样
  - FSR ≈ 21 次纹理采样/像素（EASU 16 + RCAS 5）
- **超分不能增加信息量**。它的本质是「低分辨率渲染 + 高质量放大」，
  只能减少放大带来的模糊。**源分辨率越接近显示分辨率，效果越不可见** ——
  例如 1920×960 的源在 1080p 屏上超分，几乎看不出差别；而 320×176 的源
  放大 6 倍后本身就该模糊，超分也变不出原本不存在的信息。
- **大目标档位的显存占用**：FSR 用 ping-pong 两张目标尺寸纹理。
  4320p（7680×4320）单张约 118MB，两张约 236MB；选 3840p/4320p 时需留意真机显存。
- **MEMC 目标帧率受屏幕刷新率限制**，见 [第 3 节](#3-memc-插帧)。
- **图片 / 全景模式下两者都不生效**，见 [第 1 节](#1-功能总览)。

## 7. 诊断日志

增强链内置三类低频日志（tag 均为 `VRGLRenderer`），用于区分「pass 在跑」
与「主 shader 真的采样了」这两个完全不同的状态：

| 日志 | 含义 | 判读要点 |
|---|---|---|
| `画质增强状态变更: MEMC=..@..fps FSR=..@WxH` | 开关是否真的传到了渲染层 | 拨了开关却没打印 ⇒ `LaunchedEffect` 未触发 |
| `MEMC 运行中 #N phase=x.xx 插帧帧数=N 场景切换累计=N ...` | 每 120 帧一行 | **`phase` 必须在 0~1 之间变化**；恒为 `1.00` 就是插帧没生效 |
| `FSR 运行中 #N 源WxH -> 目标WxH` | 每 120 帧一行 | 核对目标尺寸的宽高比是否与源一致 |
| `增强纹理接入: texId=N prog=image(2D) loc[uSamplerVideo=N uIsVideo=N ...]` | 纹理是否真的被主 shader 采样 | `uSamplerVideo` 若为 **-1**，说明 sampler 被驱动优化掉、采样退回默认 unit 0（= 原图） |

`增强纹理接入` 这条最有价值：它把「pass 在跑」和「画面真的用了结果」分开验证。
正常值形如 `texId=5 prog=image(2D) loc[uSamplerVideo=39 uIsVideo=1 uSamplerImage=38]`。

| 文件 | 职责 |
|---|---|
| `app/src/main/java/com/example/vr/VideoEnhanceConfig.kt` | 枚举定义 + **纯函数规则引擎** `VideoEnhanceRules.resolveFsr()` |
| `app/src/main/java/com/example/vr/VideoEnhanceShaders.kt` | FSR：EASU + RCAS；MEMC：`me_blockmatch` / `mc_interpolate` / `frame_diff` / copy |
| `app/src/main/java/com/example/vr/VRGLRenderer.kt` | 增强链装配：`runVideoEnhance()` / `runMemc()` / `runFsr()` / `detectSceneCut()` |
| `app/src/main/java/com/example/vr/VRPlayerScreen.kt` | `SettingsSectionEnhance()`（设置面板「画质增强」分组） |

**架构约定**：UI 与渲染侧**共用同一份判定**（都调 `VideoEnhanceRules.resolveFsr()`），
杜绝「UI 显示 1440p、渲染却在用 1080p」这类两套逻辑对不上的问题。

**持久化的 prefs 键**：

```
memc_enabled            (Boolean)
memc_target_fps         (Int, 48~120)
fsr_enabled             (Boolean)
fsr_rule_mode           (String, "default" | "custom")
fsr_target_resolution   (String, "720p" | "1080p" | "1440p" | "2160p" | "3840p" | "4320p")
```

> ⚠️ 枚举一律存 **id 字符串**，不要存 ordinal（增删枚举会错位）。
